# 执行条件与写操作边界

## 工程与环境

准备顺序：定位工具与 CLI → 读取登录状态 → 列出已有项目并确定目标 → 读取工程 AppID → 用户选择测试号或真实 AppID → 按所选方式确认 AppID → 打开目标工程并探测模拟器就绪。不要将索取工程路径作为第一次环境检查的前置条件。

### AppID 选择

向用户明确提供两个选项，已有配置也不代表用户选定了类型：

- **使用测试号**：优先调用 `wechatide -c <clientName> get_user_appids --type miniprogram`，从返回账号信息确认已有测试号，核对工程配置后直接用 CLI 打开、编译和测试。已有号无需重新生成。本机实测该接口会返回名称为“louchi的接口测试号”的账号。只有列表没有可用测试号、需要新获取时，再在已登录的开发者工具 GUI 中打开新建／导入项目面板，使用 AppID 附近的“测试号”入口。不要默认要求用户去公众平台手工申请，也不要用 `automation_testaccount` 的 ticket 管理替代此入口。GUI 流程本机尚未完整验证，执行时以实际页面为准。
- **使用真实 AppID**：确认用户指定的 AppID；可读取工程现有值或有权限的 AppID 列表供选择，不自行选用其他小程序账号。

用户已明确选择时沿用。配置已存在时先读出值，说明它将被保留还是需要替换；未获修改授权不覆盖配置。不为取测试号创建无关工程或覆盖现有源码。

CLI 登录与 GUI 创建页状态需分别检查：CLI 返回已登录不保证 GUI 面板同步登录。GUI 若要求扫码，说明实际状态并完成用户授权的登录流程。取得 AppID 后以目标工程真实编译验证可用性；测试号只用于测试，发布所需的真实 AppID 另行确认。

可用读操作：`check_wechatide_status`、`project_list`、`get_user_appids`；参数以本机 CLI 帮助为准。测试号管理 `automation_testaccount` 需要已有工程路径，其 list 操作不能被假定为生成新 AppID。工具附带错误指南将空值和 `touristappid` 列为可能无效的 AppID；真实测试号须核实来源、权限和编译结果。修改现有 AppID 前取得授权并备份。

- 只操作用户指定的一个工程；不为回归或顺手验证打开其他工程。
- 命令执行会写 `.mp-autocheck/` 报告；需要工具的体检会打开/复用项目窗口、刷新模拟器及导航页面。因此“只读体检”仅指不修改工程源码，不保证应用启动和页面生命周期没有业务副作用。
- CLI、登录检测与就绪探测复用 `scripts/lib/wechatide.mjs`。不要在窗口未开或模拟器未就绪时直接调用 `automation_*`。
- 缺 CLI 时说明限制，仍可跑 `--only config`。需要安装时先核实本机官方安装器是否存在并取得安装授权，不拼接未经核实的安装路径或下载链接。
- 登录失效时说明需扫码；在用户授权登录后使用工具返回的二维码与任务 ID，不自动清除认证或更换客户端身份。
- 常规工具调用使用内部 wechatide 通道，不要求手工打开旧方案的“服务端口”。快速免重开 UI 批量检测另用本机 CDP 调试通道，首次启用须取得用户授权，之后整批复用，具体见 ui-batch.md。新 clientName 可能仍需工具内授权。
- 采集／点击／流程执行前核对模拟器当前 webview ID 与自动化页面实例 ID；不一致时停止业务操作，不能把调用返回成功或旧页面 data 当结果。可使用 scripts/lib/page-context.mjs 校验。修复通道经授权在原窗口刷新模拟器一次，不清缓存、不清登录；修复后必须验证跨页导航及截图和页面 ID 一致，再恢复检测。没有自动刷新或自动重启策略。
- 调用无响应时停止该层并保留已有证据，不盲目反复调用或强杀。必要的关窗重开先确认用户授权和未保存工作；不把通道错误判为应用错误。

## 第三层：点击

使用独立命令 `tap-check.mjs`，不接入体检长流程。

只点击静态可确定为导航的入口；动态路径无法确定、选择器不唯一或前置条件不清楚时跳过。保留原库对路径拼接与查询参数的识别规则，不为扩大覆盖随意放宽。

导航方法也可能包含额外写入，页面生命周期也可能调用服务。读取相关处理逻辑，确认操作处于授权范围；危险入口不点击。导航后核对页面，必要时核对状态；结束复位首页。

## 第四层：流程

先按 [完整任务识别与流程测试](flow-testing.md) 建立所有任务的清单及入口映射，再按任务生成场景；不能只识别核心任务或直接以原表单脚本代替完整流程。

明确要完成的任务、预期结果、数据条件和可能副作用，再执行。优先使用隔离测试环境与可丢弃数据；仅恢复本地 storage 无法撤销服务端提交、云数据库写入、消息发送或发布。

当前 `ux-check.mjs` 及 `ux-audit.mjs` 有以下实现限制，本版保留代码，不能依赖其“不留测试数据”注释：

1. `storageDump()` 读取失败时返回 `'{}'`，与空存储混淆；`storageRestore()` 可能据此清空原有数据。
2. 收尾恢复不在 `finally` 中，异常退出可能跳过恢复；备份仅在内存中。
3. 恢复过程中先删除现有键，再逐项写回；中途失败可能留下部分状态，且未进行完整恢复核对。
4. “空提交”未显式清空所有输入；“正常提交”只选择一个输入并填统一值，不能自动满足多字段表单。
5. 反馈与成功结论主要基于静态提示 API、页面与 data 变化，不能替代业务结果核验。

**在存在需保留数据的工程上，不直接运行当前 UX 自动入口。** 隔离、可丢弃测试环境可运行以提供线索，仍需补充业务核验。若环境不能隔离，先修复并验证存储保护逻辑再使用该入口；不要以用户授权流程测试为由忽略已知数据缺陷。

危险操作仅检查代码和确认机制，不实际执行。点击与输入前核对选择器唯一性。非 tab 页通过“首页 → navigateTo”进入，保留真实返回栈。

补充走查以完整任务为单位：满足全部必填字段、逐步观察反馈、核对实际结果；记录卡点和必要步骤。当前工具看不到原生 toast/modal 时标明未直接观测，不把提示代码存在当成已显示。

## 机型切换

旧配置切换方式原本会修改多个项目配置；兼容脚本已改为精确定位 `hash_key_map*.json` 中 `toolbar_<项目绝对路径>` 对应的配置文件，只修改目标项目。新格式 `ls_<hash>.json` 优先于旧格式 `localstorage_<hash>.json`。映射不存在或多个用户目录同时匹配时拒绝猜测。

默认复用已开启的本机调试通道：定位路径完全匹配的目标项目窗口 → 工程外备份原机型／页面 → 调用工具原生机型切换动作 → 实际设备名称、屏幕尺寸及像素密度连续两次匹配后检测。整批复用连接和 Automator 桥接，不逐机型重开，不点击 GUI。首次开启调试通道需要用户授权的一次重启，脚本不自行执行。异常退出进入 finally 恢复并核验原机型／页面；恢复失败保留备份并报告。旧的关闭、改配置、打开方式仅在用户明确允许时选 `--device-switch restart`。

独立 `ui-check.mjs --matrix` 会自动完成批量切换；`selfcheck.mjs --device` 兼容入口转交该命令，不再随机型重复编译。详见 [ui-batch.md](ui-batch.md)。

## 后续脚本修改的验证目标

如用户要求继续修脚本，针对实际风险验证行为，而非只检查文字：

- 存储读取失败、返回异常或非法 JSON：不执行点击、输入或删除存储。
- 备份成功：保存可恢复副本；执行抛异常也进入收尾；恢复后核对所有键和值。
- 机型切换：只修改已确定归属的配置，无法确定归属时不写入。
- 多字段任务：测试数据满足预期；未满足时记录未完成，而非正常提交失败。

运行 `selftest.mjs` 只是纯函数回归；以上副作用保护需要额外验证，不能凭原有 70 项通过宣称已修复。

## 代码测试补查

运行第一层时读取 [code-testing.md](code-testing.md)。脚本输出之后仍须核对各诊断面板和相关终端结果；不得将面板中的代码诊断划入 UI 测试或留到第三、四层。现有脚本没有自动读取这些全部来源，因此执行者负责补充证据与覆盖状态。
