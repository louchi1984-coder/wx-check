# 执行条件与写操作边界

## 工程与环境

准备顺序：定位工具与 CLI → 读取登录状态 → 列出已有项目并确定目标 → 读取工程 AppID → 询问用户是否有 AppID → 有则确认，没有则让用户在 GUI 手动选择测试号 → 核对最终 AppID → 打开目标工程并记录编译及模拟器状态 → 按用户选择的范围检测。编译失败不阻断静态代码测试；依赖模拟器的检查须实际就绪。不要将索取工程路径作为第一次环境检查的前置条件。

### AppID 选择

登录确认后询问：“你有要使用的小程序 AppID 吗？”用户在本次任务中已经回答过时沿用，不重复询问。已有配置先读出并供用户确认，不能仅凭 ID 格式判断真实账号或测试号，也不能把已有配置当作用户已经选定。

- **有 AppID**：让用户提供或确认工程已有 AppID，也可读取有权限的账号列表供用户选择。确认对应目标工程，不自行选用其他账号。
- **没有 AppID**：调出同一开发者工具的新建／导入项目界面，指明 AppID 附近的“测试号”入口，让用户手动选择。不要继续尝试用 CLI 生成测试号，不默认从账号列表替用户挑选，也不填写固定、猜测的测试 ID。入口文字和位置以实际界面为准；无法控制窗口时给出手动打开步骤并如实说明限制。

用户完成选择后读取目标工程实际配置，核对得到的 AppID，再打开工程、真实编译并确认模拟器就绪。没有完成选择或无法确认时暂停依赖 AppID 的运行测试；用户已选代码测试时仍可检查静态配置，不能假称导入成功。已有可用测试号且用户明确确认继续使用时，不要求重新生成。

配置已存在时先说明将使用的值；修改现有 AppID 前取得授权并备份。不为获取测试号创建无关工程、覆盖源码或重复导入。GUI若出现登录界面，按 [login.md](login.md) 的手动扫码分支处理，不把创建页未同步笼统解释为登录失败。测试号用于测试，发布前另行确认真实 AppID。

可用读操作：`check_wechatide_status`、`project_list`、`get_user_appids`；参数以本机 CLI 帮助为准。测试号管理 `automation_testaccount` 需要已有工程路径，其 list 操作不能被假定为生成新 AppID。工具附带错误指南将空值和 `touristappid` 列为可能无效的 AppID；真实测试号须核实来源、权限和编译结果。修改现有 AppID 前取得授权并备份。

- 只操作用户指定的一个工程；不为回归或顺手验证打开其他工程。
- 命令执行会写 `.mp-autocheck/` 报告；需要工具的体检会打开/复用项目窗口、刷新模拟器及导航页面。因此“只读体检”仅指不修改工程源码，不保证应用启动和页面生命周期没有业务副作用。
- CLI、登录检测与就绪探测复用 `scripts/lib/wechatide.mjs`。不要在窗口未开或模拟器未就绪时直接调用 `automation_*`。
- 缺 CLI 时说明限制，仍可跑 `--only config`。需要安装时先核实本机官方安装器是否存在并取得安装授权，不拼接未经核实的安装路径或下载链接。
- 登录失效时说明需扫码；在用户授权登录后使用工具返回的二维码与任务 ID，不自动清除认证或更换客户端身份。
- 常规工具调用使用内部 wechatide 通道，不要求手工打开旧方案的“服务端口”。快速免重开 UI 批量检测另用本机 CDP 调试通道，首次启用须取得用户授权，之后整批复用，具体见 ui-batch.md。新 clientName 可能仍需工具内授权。
- 采集／点击／流程执行前核对模拟器当前 webview ID 与自动化页面实例 ID；不一致时停止业务操作，不能把调用返回成功或旧页面 data 当结果。可使用 scripts/lib/page-context.mjs 校验。修复通道经授权在原窗口刷新模拟器一次，不清缓存、不清登录；修复后必须验证跨页导航及截图和页面 ID 一致，再恢复检测。没有自动刷新或自动重启策略。
- 调用无响应时停止当前检测项目并保留已有证据，不盲目反复调用或强杀。必要的关窗重开先确认用户授权和未保存工作；不把通道错误判为应用错误。

## 点击测试

使用独立命令 `tap-check.mjs`，不接入体检长流程。

只点击静态可确定为导航的入口；动态路径无法确定、选择器不唯一或前置条件不清楚时跳过。保留原库对路径拼接与查询参数的识别规则，不为扩大覆盖随意放宽。

导航方法也可能包含额外写入，页面生命周期也可能调用服务。读取相关处理逻辑，确认操作处于授权范围；危险入口不点击。导航后核对页面，必要时核对状态；结束复位首页。完整点击测试还需按 [click-testing.md](click-testing.md) 补测业务按钮，脚本限制不能被当作整项检测范围。

## 流程测试

先按 [完整任务识别与流程测试](flow-testing.md) 建立所有任务的清单及入口映射，再按任务生成场景；不能只识别核心任务或直接以原表单脚本代替完整流程。

明确要完成的任务、预期结果、数据条件和可能副作用，再执行。优先使用隔离测试环境与可丢弃数据；仅恢复本地 storage 无法撤销服务端提交、云数据库写入、消息发送或发布。

`ux-check.mjs` 是表单辅助检查，不能替代完整业务场景。开始业务操作前严格读取本地存储并在工程外落盘备份，读取失败、值无法可靠备份或备份文件写入失败则停止。收尾在 `finally` 中执行：先写回所有原键，再删除新增键，最后核对全部键和值；失败保留备份与恢复前状态，并报告未完成。测试期间不得有其他人或程序同时写入该存储。

空提交先清空并核对全部输入；多字段正常提交须提供 `--values-file`，按页面路径映射各选择器的合法字符串值。缺值、选择器不唯一或控件不支持时记录未覆盖。单字段 `--fill` 也必须按业务约束确认合法。页面跳转或 data 变化仅是响应线索，保存是否成功必须读回实际记录验证。服务端数据保护仍需隔离环境或单独恢复方案。

原UX脚本不执行危险操作；完整流程测试中的删除、清空、导出等任务不能因此漏掉。仅在相关操作明确授权、测试数据可隔离且恢复方案可靠时，用单独设计的场景实际执行；否则记录未覆盖，不将静态确认机制检查写成实测通过。点击与输入前核对选择器唯一性。非 tab 页通过“首页 → navigateTo”进入，保留真实返回栈。

补充测试以完整任务为单位：满足全部必填字段、逐步观察反馈、核对实际结果；记录卡点和必要步骤。当前工具看不到原生 toast/modal 时标明未直接观测，不把提示代码存在当成已显示。

## 机型切换

旧配置切换方式原本会修改多个项目配置；兼容脚本已改为精确定位 `hash_key_map*.json` 中 `toolbar_<项目绝对路径>` 对应的配置文件，只修改目标项目。新格式 `ls_<hash>.json` 优先于旧格式 `localstorage_<hash>.json`。映射不存在或多个用户目录同时匹配时拒绝猜测。

默认复用已开启的本机调试通道：定位路径完全匹配的目标项目窗口 → 工程外备份原机型／页面 → 调用工具原生机型切换动作 → 实际设备名称、屏幕尺寸及像素密度连续两次匹配后检测。整批复用连接和 Automator 桥接，不逐机型重开，不点击 GUI。首次开启调试通道需要用户授权的一次重启，脚本不自行执行。异常退出进入 finally 恢复并核验原机型／页面；恢复失败保留备份并报告。旧的关闭、改配置、打开方式仅在用户明确允许时选 `--device-switch restart`。

独立 `ui-check.mjs --matrix` 会自动完成批量切换；`selfcheck.mjs --device` 兼容入口转交该命令，不再随机型重复编译。详见 [ui-batch.md](ui-batch.md)。

## 后续脚本修改的验证目标

如用户要求继续修脚本，针对实际风险验证行为，而非只检查文字：

- 存储读取失败、返回异常或非法 JSON：不执行点击、输入或删除存储。
- 备份成功：保存可恢复副本；执行抛异常也进入收尾；恢复后核对所有键和值。
- 机型切换：只修改已确定归属的配置，无法确定归属时不写入。
- 多字段任务：测试数据满足预期；未满足时记录未完成，而非正常提交失败。

运行 `selftest.mjs` 只是纯函数回归；以上副作用保护需要额外验证，不能凭原有 70 项通过宣称已修复。

## 代码测试补查

运行代码测试时读取 [code-testing.md](code-testing.md)。脚本输出之后仍须核对各诊断面板和相关终端结果；不得将面板中的代码诊断划入 UI测试或留到点击测试与流程测试。现有脚本没有自动读取这些全部来源，因此执行者负责补充证据与覆盖状态。

## 等待限制与报告保存

登录诊断的20秒单次/90秒总计是登录流程要求，执行时必须显式设置外层时限，不能直接沿用库默认值。当前ensureReady的90秒不包含刷新时间，且同步探测可能越过截止时间；不能向用户承诺整个准备流程90秒完成。未修改这一实现前，记录真实耗时并限制重试，不以加长等待代替排障。UI扫描只在命中特定automator超时时等待20秒恢复一次，每轮最多一次；正常扫描不加固定等待。

代码、点击、流程原始报告会覆盖同名文件，每次命令后立即另存到工程外本轮目录。统一用户报告和UI图片都在工程外，JSON/日志是附件。检测完成不要求先修复；修复授权已有时，每项报告后处理并重测，再继续，UI测试最后。
