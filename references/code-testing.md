# 第一层：代码测试——程序有没有写对

## 范围与分工

检查工程代码、配置、构建与运行的正确性。诊断位于 GUI 中，不意味着它属于第二层 UI 测试；第二层检查被测小程序界面显示。

现有 `selfcheck.mjs` 提供配置、WXML/WXSS 编译、console/network 和绑定字段的部分证据。它没有采集所有开发者工具面板；agent 必须补查，不能仅运行脚本后宣布第一层完成。

## 必查来源

| 来源 | 检查内容 | 证据要求 |
|---|---|---|
| 静态配置与资源 | 页面、组件、资源引用、AppID、编译配置 | 目标工程、文件位置及实际配置；复用模块 A |
| 真实编译 | WXML/WXSS 编译与实际错误文件；相关 JS 错误通过构建/运行诊断补查 | 编译结果、错误来源；不将入口文件当成全部错误归属 |
| 构建面板 | 编译、构建任务失败和告警 | 任务时间、结果、具体消息；区分本次和历史任务 |
| 调试器 | Console 的 error/warning、Network 失败请求和异常响应 | 展开实际明细，解释来源与影响；不只看数字 |
| 问题面板 | 语法、类型、配置或扩展诊断 | 文件、行号、消息；区分工程问题与扩展自身问题 |
| 输出面板 | 本工程相关构建器、扩展或工具输出 | 查看相关通道；无关通道不计入工程问题；必要时保留失败上下文 |
| 调试控制台 | 调试会话的异常和命令失败 | 对应会话、时间与消息；未启动相关会话时标不适用，不虚报通过 |
| 代码质量 | 展开各检查类别及未通过项 | 记录扫描时间；旧结果或与源码冲突时重新扫描当前工程并核对结果 |
| 相关终端 | 工程构建、lint、类型检查、测试等命令的失败 | 命令、退出码、失败明细；未运行的命令不得声称通过 |
| 业务正确性 | 用户任务或工程明确的关键业务预期 | 利用已有相关测试核验；缺少预期/数据/授权时标未覆盖，不凭编译成功作判断 |

面板可用 CLI/API 读取时优先使用；没有接口或结果与可见 GUI 不一致时使用 GUI 补查。不要为保持“纯 CLI”而漏掉诊断，也不要假定 CLI console 缓冲区等于调试器全部消息。

## 执行顺序

1. 确认单一目标工程和环境；读取工程已有测试/构建命令与相关配置。
2. 运行静态与真实编译、运行采集；不为代码体检执行未经授权的业务写操作。
3. 核对上表各诊断来源。旧结果区分时间；需要复扫时对当前工程复扫。终端只核对本工程相关命令，按实际需要运行已有检查，不安装依赖或修改配置来凑通过结果。
4. 对照 CLI 报告、GUI 消息与文件配置。数量不一致不能取较少的一边当最终结论；记录采集遗漏与原始消息。
5. 逐项解释问题并形成第一层报告；修复另按主说明的备份、最小修改、复验和回滚规则执行。

## 每条诊断如何报告

记录来源、原始消息、位置/时间、含义、影响、处理建议与确定性：

- 工程缺陷：提供文件或业务证据与可复验预期。
- 工具/基础库/浏览器告警：解释其含义和当前影响，不能省略或自动算成业务缺陷；归因不充分时写“待确认”。
- 旧记录：保留旧失败与复扫后的新结果，不把旧失败说成当前未通过，也不直接忽略它。
- 工具或采集失败：标为检查失败/无结论，不能转成应用通过。

不要仅凭警告数字宣称有几个代码缺陷，也不要凭没有 error 宣称零问题。基础库环境提醒、资源 preload 警告等同样需要解释，但不一定需要修改业务代码。

## 完成与结果措辞

第一层完整检查完成，需要所有必查来源有明确状态，适用项均取得当前工程证据，全部发现得到解释，相关复验完成。发现尚未解决的问题时可以说“检查完成，仍有问题”，不能说“测试通过”。

有检查失败、无法读取或应测未测项时，只能说“部分检查完成”，列出缺口。确实没有对应会话、构建任务或终端命令的项目可以标不适用并说明依据，不能用不适用掩盖漏查。

报告保留脚本原始结果与补充诊断，不改写原始采集值掩盖缺陷。第一层至少列出：覆盖状态表、问题/告警明细、历史与本次结果的区别、已修复及复验、未覆盖范围。

## 处理发现

按照 [repair.md](repair.md) 选择检测项修复或完整修复。检测中发现其他层的问题可以记录并在授权内处理，但必须保留归属及复验边界。不能把异常提示修复或单项通过当成完整业务修复。
