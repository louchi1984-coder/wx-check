# 代码测试——程序有没有写对

## 范围与分工

检查工程代码、配置、构建与运行的正确性。诊断位于 GUI 中，不意味着它属于UI测试；UI测试检查被测小程序界面显示。

执行者结合源码与当前官方编译、日志、网络接口判断程序正确性。read-ide-diagnostics.mjs只补充构建队列、代码质量、问题列表和输出通道的原始证据，不代替判断。问题与输出读取不依赖系统无障碍；编辑器需在完整模式初始化。未读取或只读到部分时说明缺口，错误关键字须核对来源与影响。

## 工具调用与核验

先读[当前官方接口](official-tool-skill.md)中的compiler、debugger说明；沿用已授权clientName和目标工程。官方命令的参数示例见该说明，路径与运行时配置见[工具细节](tool-details.md)。已有本轮连接记录先读取并沿用；首次CDP验证后按[通道说明](debug-channel.md#3-验证并使用)保存记录。

| 检查目标 | 调用工具 | 怎样确认结果 | 失败后怎么办 |
| --- | --- | --- | --- |
| 实际运行页与完整模式 | open_project_window、automation_runtime_info | 工程路径正确，返回具体页面；内部读取的编辑器服务可用 | reuse不代表已转为完整模式；按已有授权处理重开，不自动重置 |
| WXML/WXSS编译 | compile_wxml / compile_wxss，--file-path相对miniprogramRoot | 核对完整返回、实际错误文件与消息；成功不代表JS及整包通过 | 保留错误，继续其他来源；不安装依赖来凑通过 |
| 调试器日志与请求 | get_simulator_console / get_simulator_network，--command "grep -n ." | 逐条解释error/warning和失败请求，核对采集时间与范围 | 空缓冲不证明无异常；按实际可用面板或绑定日志补查 |
| 构建、代码质量、问题、输出 | prepare-debug-channel.mjs后调用read-ide-diagnostics.mjs | 通道ready、projectMatches为1、protocol.available为true；核对quality、build.scope、problems.available及output通道的available/complete/truncated | 按[通道说明](debug-channel.md)处理一次；用可用的绑定日志或获准界面补查，不能拿console替代代码质量 |
| 调试控制台、相关终端及工程已有检查 | 当前debugger接口、会话记录及已有命令 | 对应会话、完整消息、退出码和检查范围 | 确无对应会话或命令才标不适用；未查到、没运行不能标通过 |

内部读取调用如下；脚本路径、端口和输出路径替换为当前实际值，输出放工程外：

```sh
node "<skill绝对目录>/scripts/read-ide-diagnostics.mjs" --project "<工程绝对路径>" --port <已验证实际端口> --out "<工程外诊断JSON路径>"
```

通道准备在代码测试内完成，不等到UI测试。通道受阻不影响源码、官方编译和可用日志检查，但构建、问题、输出和代码质量仍是必查来源；逐项补查，确实无法读取时保留缺口并交付部分完成的代码报告。不得从“没找到面板专用命令”推断“没有诊断接口”，也不得把接口片段称为面板全部内容。

## 必查来源

| 来源 | 检查内容 | 证据要求 |
|---|---|---|
| 静态配置与资源 | 页面、组件、资源引用、AppID、编译配置 | 目标工程、文件位置及实际配置 |
| 真实编译 | WXML/WXSS 编译与实际错误文件；相关 JS 错误通过构建/运行诊断补查 | 编译结果、错误来源；不将入口文件当成全部错误归属 |
| 构建面板 | 编译、构建任务失败和告警 | 任务时间、结果、具体消息；区分本次和历史任务 |
| 调试器 | Console 的 error/warning、Network 失败请求和异常响应 | 展开实际明细，解释来源与影响；不只看数字 |
| 问题面板 | 语法、类型、配置或扩展诊断 | 文件、行号、消息；区分工程问题与扩展自身问题 |
| 输出面板 | 本工程相关构建器、扩展或工具输出 | 查看相关通道；无关通道不计入工程问题；必要时保留失败上下文 |
| 调试控制台 | 调试会话的异常和命令失败 | 对应会话、时间与消息；未启动相关会话时标不适用，不虚报通过 |
| 代码质量 | 展开各检查类别及未通过项 | 记录扫描时间；旧结果或与源码冲突时重新扫描当前工程并核对结果 |
| 相关终端 | 工程构建、lint、类型检查、测试等命令的失败 | 命令、退出码、失败明细；未运行的命令不得声称通过 |
| 业务正确性 | 用户任务或工程明确的关键业务预期 | 利用已有相关测试核验；缺少预期/数据/授权时标未覆盖，不凭编译成功作判断 |

面板可用 CLI/API 读取时优先使用；没有接口或结果与可见 GUI 不一致时使用 GUI 补查。不要为保持“纯 CLI”而漏掉诊断，也不要假定 CLI console 缓冲区等于调试器全部消息。

## 执行顺序

1. 确认单一目标工程和环境；读取工程已有测试/构建命令与相关配置。用官方open_project_window --window-mode fullMode打开，默认liteMode只有模拟器；核对编辑器服务已经初始化，开窗命令成功不能代替此项。已有业务测试进行中时不切换其窗口，先收尾。
2. 运行静态与真实编译、运行采集；不为代码体检执行未经授权的业务写操作。
3. 核对上表各诊断来源。旧结果区分时间；需要复扫时对当前工程复扫。终端只核对本工程相关命令，按实际需要运行已有检查，不安装依赖或修改配置来凑通过结果。
4. 对照 CLI 报告、GUI 消息与文件配置。数量不一致不能取较少的一边当最终结论；记录采集遗漏与原始消息。
5. 逐项解释问题并形成代码测试报告；修复另按主说明的备份、最小修改、重测和回滚规则执行。

## 每条诊断如何报告

记录来源、原始消息、位置/时间、含义、影响、处理建议与确定性：

- 工程缺陷：提供文件或业务证据与可重复验证预期。
- 工具/基础库/浏览器告警：解释其含义和当前影响，不能省略或自动算成业务缺陷；归因不充分时写“待确认”。
- 旧记录：保留旧失败与复扫后的新结果，不把旧失败说成当前未通过，也不直接忽略它。
- 工具或采集失败：标为检查失败/无结论，不能转成应用通过。

不要仅凭警告数字宣称有几个代码缺陷，也不要凭没有 error 宣称零问题。基础库环境提醒、资源 preload 警告等同样需要解释，但不一定需要修改业务代码。

## 完成与结果措辞

代码测试完整检查完成，需要所有必查来源有明确状态，适用项均取得当前工程证据，全部发现得到解释，必要的检查结果复核完成；不要求先修复问题才能完成检测。发现尚未解决的问题时可以说“检查完成，仍有问题”，不能说“测试通过”。

有检查失败、无法读取或应测未测项时，只能说“部分检查完成”，列出缺口。确实没有对应会话、构建任务或终端命令的项目可以标不适用并说明依据，不能用不适用掩盖漏查。

System Events或窗口可访问性报-10004，只证明那次调用被拒绝；不能据此判断所有读取途径不可用。保留stderr和真实退出码，先使用已经可用的内部服务与通道绑定日志。内部读取也受阻时明确阻塞项和所需操作，不循环提权、重启或直接宣布代码测试完成。

报告保留脚本原始结果与补充诊断，不改写原始采集值掩盖缺陷。代码测试至少列出：覆盖状态表、问题/告警明细、历史与本次结果的区别、已修复及重测、未覆盖范围。

## 处理发现

按照 [repair.md](repair.md) 选择检测项修复或完整修复。检测中发现其他测试项目的问题可以记录并在授权内处理，但必须保留归属及重测边界。不能把异常提示修复或单项通过当成完整业务修复。

## 统一交付要求

面向用户的报告必须遵守 [检测报告统一规范](reporting.md)，使用固定模板、状态和必填证据；本文件的专门要求填写在模板对应栏目，不另创报告格式。

接口按当前安装发现和核验，不按固定版本限制；版本只用于记录证据和排查差异，不能因版本不同跳过检测。
