# 微信开发者工具操作与采集边界

需要排查编译归因、采集遗漏、选择器、返回结构或无响应时读取。下文保留原包的技术记录；它们是原作者的环境实测记录，不代表已在当前机器复验。

## 当前代码优先于历史记录

- `selfcheck.mjs` 实际运行顺序是 A → C → D → E → B，没有独立运行的 F 模块。
- `wechatide.mjs` 当前同步封装使用 `spawnSync`，输出直接写临时文件；不要把历史“管道超时无效”推广成当前封装必然无法超时，也不要擅自换回输出管道。
- 本技能使用 `wx.getWindowInfo()`，避免向被测程序 console 注入废弃 API 告警。
- 历史记录中的“未留测试数据”“存储备份失败不会清空数据”不适用于当前 UX 脚本。执行条件见 [execution.md](execution.md)。

## 采集与判定边界


- **界面模块只查得到带 `class` 的元素**。该运行环境下选择器仅支持 class（标签与通配符均返回 0），无 class 的裸容器拿不到坐标。规则因此设计为「靠有 class 的元素暴露问题」。
- **不做元素重叠检测**。判断两个框相交需要 DOM 父子关系，采集数据里没有，父子天然重叠会变成误报。宁可少一条规则，不要一条天天喊狼来了的规则。
- **文字截断检测有明确边界**。做法是：静态找出带 `text-overflow: ellipsis` 的 class → 读元素文字 → 用离屏画布量出文字实际宽度 → 与元素宽度比。为什么不直接用 `fields({computedStyle})`：见下文环境坑，它会把整轮体检打废。
  已知边界，报的时候要带上：①**只量每个 class 的第一个实例**（`automation_element_action` 按选择器只返回首个命中），列表里第二行之后不覆盖；②量宽度用的字体可能与真实渲染字体不同，因此留了容差 `max(4px, 元素宽 × 8%)`，**宁可漏报不误报**；③只查静态写了 `ellipsis` 的类，靠行数裁剪（`-webkit-line-clamp`）的多行截断查不到。
- **`scrollWidth` 动作不能用来判截断**：它只支持 `scroll-view` 组件，对普通 `view` 直接报 `Cannot manipulate component scroll-view, got view`。
- **`compile_wxml` / `compile_wxss` 的 `--file-path` 不是「只编这一个文件」，而是「以它为入口触发一次整个工程的编译」，返回的是全工程的结果。**（实测：夹具里 `ok.wxml` 完全正确，但同工程 `bad.wxml` 有语法错时，编 `ok.wxml` 返回的报错是 `./pages/bad/bad.wxml:4:1: unexpected end`——与编 `bad.wxml` 的返回逐字相同。）
  所以**绝不能把结果归因到 `--file-path` 指定的那个文件**：会把无辜文件报成「编译不通过」，同一个错误还会按文件数重复报（夹具 2 个错被报成 4 个文件）。
  正确做法：**wxml / wxss 各只调一次**，再用 `parseErrorFiles()` 从报错文本里反查真实出错的文件（正则要求文件名以字母数字开头，避免把报错里的 `.wxss` 这种光扩展名当成文件；再用「路径在工程里确实存在」二次确认）。报错里没给文件名时（wxss 常见），只报「这一类整体编不过」，**不点名文件**。
- **真编译只覆盖 wxml/wxss 的编译产物**，不等于整包构建成功。`build_npm` 会改本地产物，所以**只检测不执行**：发现声明了 npm 依赖却没有 `miniprogram_npm` 时只提示用户去开发者工具点「构建 npm」。
- **工程配置类报错和「文件编不过」必须分开**：AppID 无效（`APPID_ERROR`）或报错以 `app.json:` / `project.config.json:` 开头时，编译器对任何文件都回同一句，这是**全局问题**。此时若一个文件都没编过，标记为「无法真编译 / 无结论」，而不是报成一堆「编译不通过」。
- **绑定字段检查是 P1**：`{{ foo }}` 在页面 data 与 js 的 data 初值里都找不到才报，且字段也可能只在交互后才 `setData`，所以报告里写明「需人工确认」。`wx:for` 的 item/index 别名、函数调用名、字符串字面量里的词都已排除，避免误报。
- **「点几下、回首页几下」以模块 G 的实测为准**：静态推算已从体检中移除，因为动态拼接的 url（`'/pages/a/a?id=' + id`）静态解析不了，实测点击才能给出可信数字。
- **真点击（模块 G）的安全边界，不要放宽**：只点**静态能确定是导航**的元素——wxml 的 `bindtap` 能按名字对上 js 里同名方法、且方法体里有字面量 url 的导航调用。工程里可能有「清空全部数据」这类按钮，乱点就是破坏。因此它是**写操作**，用独立命令 `scripts/tap-check.mjs` 执行。
- **体验走查（模块 H）：能判什么、判不了什么，必须如实说**
  - **判不了「有没有弹提示」**：toast / showModal 是微信**原生层**渲染，页面 DOM 里查不到（实测 `.wx-toast` / `.weui-toast` / `.wx-modal` 等选择器全部命中不到）。所以结论不是"看见"的，而是**交叉判定**出来的 —— 静态看提交方法体里有没有 `showToast/showModal` 这类提示代码，运行时看当前页变没变、页面 data 变没变。报告里必须带上这个判据，别让人误以为工具看得见提示。
  - **同样判不了**：配色、字号、间距、文案是否通顺、图标是否易懂。模块 H 给的是**行为层面**的体验结论，不是审美结论——审美仍需人看。
  - **只走静态能确认的提交按钮**：文案含保存/提交/确定/完成/添加/创建/发布/发送/登录，**且这一页真的有输入框**。没有输入框的页面整页不产生任务——否则「记一笔支出」这种纯导航按钮会被误判成提交，进而误报「空提交也能过」。
  - **任何点击 / 输入前先用 `querySelectorAll` 数元素，只有恰好命中 1 个才操作**，命中多个一律不动。多元素时按选择器点击会落到**第一个**匹配上——这正是之前「点错了元素、还顺手改写了数据」的根因。
  - **危险操作永不点击**，只做静态判定（提交方法体里有没有 `wx.showModal`）。
  - **非 tab 页必须 `navigateTo` 进入、不能 `reLaunch`**：`reLaunch` 会把页面栈压成 1 层，页面里提交后的 `wx.navigateBack()` 无处可退、静默失败，于是被误判成「提交成功但没变化」。真实用户是从首页点进去的（栈 2 层），所以走查统一「先回首页 → 再 navigateTo」。
  - **会真写数据，但开始前全量备份本地存储、结束后原样还原**；备份取不到就**宁可不还原**，绝不做「先清空再解析失败」这种把用户数据清掉的事（踩过：evaluate 的返回值比别的工具多嵌一层，取错了就拿到 `[object Object]`，`JSON.parse` 变空对象，数据直接被清）。
  - **判据要区分「谁的问题」**：走查方式本身会造假结论（栈深度、取错返回结构都算），发现"应用异常"时先确认不是走查自己弄出来的，再下结论。
- **自动化调用会「无响应」而不是报错，而且此时代码里的超时形同虚设**：实测 `automation_navigate` / `automation_element_action` 在某些上下文里会挂住不返回，`execFileSync` / `spawnSync` 的 `timeout` 不生效（子进程可能还有孙进程持有输出管道），换成异步封装后连自己的兜底定时器都触发不了（事件循环被同步调用占住），最后只能把整个 node 进程杀掉。**而强杀之后通道会留在坏状态，后续调用一律不通，必须 `close_project_window` + `open_project_window` 重开窗口才能恢复。**
- **真点击走查必须用「独立进程 + 同步调用」**：实测同一段调用，在独立脚本里跑正常，放进 `selfcheck.mjs` 的长流程尾部就挂死；改成异步封装同样挂死。所以 `tap-check.mjs` 是独立入口，`selfcheck.mjs` 只提示、不执行它（也保证体检报告一定能落盘）。
- **复位首页不要在 `automation_evaluate` 里执行 `wx.reLaunch`**：实测会把调用挂死、整轮再无输出。要用官方的 `automation_navigate`（tab 页用 `switchTab`，非 tab 页用 `reLaunch`）。
- **真点击每次先 `wx.reLaunch` 回首页**再开始，保证同一个起点、结果可比较；走完再复位回首页，不把用户留在二级页。只验证「进得去」，不深入页面内部继续点、不动数据。
- **「点了没反应」报 P1 而不是 P0**：也可能是该入口需要登录/权限等前置条件，属正常，报告里写明可忽略。
- **路径拼接的 url 必须判为「解析不了」**：`'/pages/d/' + id` 只能取到 `pages/d/` 这个**并不存在的页面**，拿去点击会点错地方。判据是「字面量之后还有 `+`，且字面量里没有 `?` 作为路径/参数分界」——`'/pages/add/add?type=' + t` 属安全（取 `?` 前部分），`'/pages/d/' + id` 属不安全。
- **别盲扫 js 里所有方法名**：`Page({` 这种函数调用会被误认成方法定义，而且匹配会把后面的 handler 一起吞掉，导致真正的入口漏掉。要按 wxml 里实际出现的 handler 名**精确查找**。
- **不做纵向溢出检测**。列表页天然比一屏长，判成溢出等于天天喊狼来了。只查横向溢出。
- **触控区 44×44 是 Apple 的标准**，小程序按钮普遍做 30px 高，原样报会刷屏，因此**跨页聚合为一条**并标注「可忽略」。
  报出的是元素**真实挂载的全部 class**（按 wxml 书写顺序），不是碰巧先匹配上的那一个 —— `class="btn btn-ghost month-btn"` 会把三个类都列出来。因为高度实际由更具体的 `.month-btn` 决定，只报 `.btn` 会把人引去改一个本来就达标的类。
- **触控区是模块级结论，不按页重复计数**。否则「合计 P1」会把同一类问题数好几遍，出现「合计 3 处、明细只有 2 条」这种对不上。
- **条件渲染未出现的元素查不到**，报告末尾会列为「未取到数据的 class」，属正常。
- **不做审美判断**（间距、配色、层级）。
- 单次数据返回有 64KB 上限，脚本已内部分批（每批 8 个 class）并带二分降级。
- **采集不到任何元素时结论不可信**。脚本会显式警告，而不是给出「P0 0」让你误以为通过。
- **模拟器未就绪时模块标记为「已跳过」**，合计处会提示结论不完整——不会静默算作通过。


## 环境兼容记录


- **工程首次打开必须先等模拟器就绪**：`ensureReady()` 已内置（先 `simulator_refresh`，再轮询 `automation_evaluate` 直到有响应）。新工程或开发者工具刚重启时 automator 还没连上，此时采集会**静默返回空数组**而不是报错——这一步不能省，也不能用固定 sleep 代替。
- **不要用 `fields()`**：见上文「局限」。批量采集只用 `boundingClientRect()`。
- **`automation_element_action --action style --name <属性>` 必须用 CSS 的连字符写法**（`font-size`、`text-overflow`）。写驼峰（`fontSize`）不报错，但**静默返回空字符串**——会让人以为要素没设这个样式。
- **各工具的返回结构不统一，别猜**：`automation_page_action --action getData` 的数据在 `result.data`；`automation_element_action --action text` 的 `result` **直接就是字符串**（不是对象）；`--action size` 是 `result.{width,height}`；`compile_wxml/wxss` 成功只回 `{success:true, codeLength}`，失败回 `{ok:false, message}` 且**进程退出码 1**，所以判据就是 `result.success`。改这些代码前先 `wechatide -c <clientName> <tool> --help` 再实跑一次看真实返回。
- **窗口没打开时 `automation_*` 调用会「挂住」而不是报错退出**（实测进程被 SIGTERM 杀掉，什么信息都不给）。更阴的是：**被强杀之后 automator 连接会留在坏状态**，之后连 `simulator_refresh` 都救不回来，所有调用一律 timeout、`ensureReady` 永远探测不到就绪。
  修法是 `close_project_window` 再 `open_project_window` 重开窗口。所以：**不要对没开窗口的工程发起 `automation_*` 调用**，也不要强杀正在飞的 `wechatide` 调用。
- **`simulator_refresh` 成功 ≠ 编译通过**（官方文档明说「不返回编译结果」）。要判编译得用 `compile_wxml` / `compile_wxss`。
- **`wechatide` 的输出不能按「从第一个 `{` 切到结尾」解析**：stdout 前有 `[wechatide] skill-call:` 日志，调用失败时 stderr 还会被拼在后面。必须做括号配平扫描，只取第一个完整 JSON 对象。
- **运行时模块必须先 `simulator_refresh` 再调一次 `automation_evaluate`**，建立 automator 连接后 console / network 缓冲区才开始回传；否则 grep 永远返回空。
- **缓冲区是懒刷新的**：重编译 + 启动 + 首屏请求有先后，单次读容易读早。脚本分 3 轮读、每轮间隔 3 秒，拿到结果就提前收工。
- **两种缓冲区格式不同**：console 记录之间用 `--` 独占一行分隔，network 每条一行。解析必须都兼容，否则 network 会被整个吞掉。
- **`selectViewport()` 与 `.in(page)` 组合会报 `__wxWebviewId__` undefined**，视口尺寸只能从页面上下文取：用 `wx.getWindowInfo()`。
  这里**不要用 `wx.getSystemInfoSync()`** —— 采集脚本是以 `automation_evaluate` 注入到**被测小程序内部**执行的，调废弃 API 会往被测小程序自己的 console 里塞一条 deprecation 告警，把模块 C 的判读搅浑（分不清是工程的问题还是体检工具造成的）。这是本工具自身的「污染被测对象」问题，已经踩过一次。
- **连续 3 批采集失败即熔断**：说明通道已无响应（例如某次调用把模拟器打挂），继续跑只会每批都等满超时。脚本会中止并把这之后的项标记为失败。
- **页面没渲染完就采集会静默少一批元素**（最阴的一条）。未渲染的 class 会返回**空数组**而不是报错，所以既不算调用失败、也不进「未取到数据」列表 —— 一声不吭地少掉一批元素。实测同一工程同一页跑两次，一次 23 个元素、一次 13 个。后果不是数字难看，而是**把本该报出来的横向溢出一起吞掉，交出一份干干净净的假报告**。
  脚本的应对：导航后等 1.8 秒；某页空 class 占比超阈值（默认三成）就再等 1.5 秒重采一次、取元素更完整的那份。
  模块 E 读到页面 data 后，这条判据会变得更准：**列表字段本来就是空的** → 空 class 完全合法，不重采、日志也改成「正常空态」（否则会虚报成「疑似渲染未完成」）；**列表里确实有内容却没元素** → 才是真没渲染完，阈值降到两成更积极重采。每页的空 class 数与 data 判定分别记在 `report.json` 的 `emptyClasses`、`dataState` 里。
- **换新的 `clientName`** 时首次调用需在开发者工具内点一次授权弹窗；沿用已授权的 clientName 可免。
- 同一元素常挂多个 class（如 `btn btn-sm btn-pri`），按 class 查询会重复命中，脚本按矩形去重。
- **`open_project_window` 的作用范围就是这个工程本身**：同一工程已开则复用；对**未打开的另一个工程**则会**再开一个模拟器窗口**（实测：用户开着 A 时对 B 跑一次，屏幕上就同时有两个模拟器）。这是工具的正常行为，**但换工程这件事必须由用户决定**——见上文「作用域」一节。
