# 流程测试：完整任务识别与流程测试

## 先完整识别所有任务

先建立整个目标应用的用户任务清单，再设计场景。不要只选核心任务、首页按钮或能被表单脚本识别的操作。完整性以当前工程、需求和可达功能证据为依据；未知需求要标明，不能宣称知道源码之外的所有任务。

遍历 app.json 的页面、分包和 tabBar；读取页面模板、交互处理、共享组件、导航关系及存储／接口逻辑。结合已提供需求，覆盖创建、查看、查找／筛选、修改、删除、设置、导入／导出、取消／返回、登录／权限，以及应用特有操作。不存在的功能不凭空添加。条件入口、空数据／有数据入口、长按、菜单和弹窗分支都要纳入；工具不可达的功能也必须列出。

任务按用户结果命名，例如“删除指定账目并使明细和统计同步”，而不是“点删除按钮”。一个任务可以跨多页，一个页面可以含多项任务。同义入口可合并任务，但不同条件、数据变化和结果必须保留分支。将每个用户可操作入口及条件分支映射到任务；无法归属的入口查明用途，未解决时写为识别缺口。仅后台内部方法不单独算用户任务。

每项记录：任务 ID、用户目标、入口与依据、前置状态、步骤、相关分支、预期最终结果、数据与副作用、验证方式、执行状态。先向用户展示完整清单和识别缺口，再执行已授权的任务，不因展示清单而重复请求已有授权。

## 从任务生成场景

每项任务均评估正常路径、合理替代路径、关键边界、取消／返回、失败与重试、结果一致性和持续有效性。适用分支要列出；不适用需说明原因，不机械穷举所有字段组合，也不默默省略难测任务。

按业务风险、已发现问题及使用频率安排顺序；排序不能缩小任务清单。共享逻辑可复用证据，但每项任务要明确引用及其适用范围。机型选择沿用用户指定或已确认的主流代表，不以旧小屏默认代替；无布局或系统差异的同一业务分支无需遍历全部 UI 机型。

## 执行与结果核验

从真实入口，通过实际元素输入、点击、选择、返回完成任务；不得直接调用业务处理函数、修改页面 data 或预填存储冒充用户操作。为隔离或故障注入设置状态时，明确区分测试准备与实际使用步骤。

同时核验过程是否顺畅、结果是否正确、失败后能否继续。观察反馈、输入保留、重复提交、键盘和滚动、返回路径；对数据任务核对实际落盘／服务端结果及关联页面，必要时重新进入或重启核验持续有效性。弹窗与页面变化不能单独证明提交成功。无法直接观察的反馈和动态体验标为未覆盖。

执行前读取 execution.md 的数据保护及副作用限制。可靠备份失败即停止写入；异常进入 finally 恢复并逐项核对。表单辅助脚本先在工程外备份本地存储，异常也尝试恢复并核对；它不恢复服务端数据，也不核验完整业务结果。授权不足、缺测试数据、危险操作或工具不可达时，保留对应任务并写明未覆盖原因；不以静态阅读代替实测通过。

## 完成与问题处理

报告包含完整任务清单，每项分别记录完成状态和检查结果，按reporting.md的统一状态表填写；分支可以记录已测通过、已测失败、未执行、不适用等实际结果，不用分支用语替代总览状态。列出总任务数、各状态数量、分支覆盖及识别缺口；核对点数、点击次数和机型重复次数不能当任务数。所有任务已识别不等于所有任务已执行。

只有清单无未解决识别缺口，且全部适用任务与选定必要分支均有实际结果，才可称本次完整流程测试完成。存在未覆盖或部分覆盖时，报告为部分完成，并具体列出缺口，不能只说“核心任务通过”。

每条问题附任务、触发步骤、预期与实际、证据、是否需要修复及理由。按 repair.md 的两种修复方式处理；保存失败须追踪最终保存结果及失败恢复，不能仅改提示文案即称解决。检测本身不自动扩大到未授权的工程修复。

## 统一交付要求

面向用户的报告必须遵守 [检测报告统一规范](reporting.md)，使用固定模板、状态和必填证据；本文件的专门要求填写在模板对应栏目，不另创报告格式。

## 表单辅助脚本的结果

`ux-check.mjs` 的 `businessResult` 未核验时，必须另行检查最终记录、统计或服务端结果，才可判定对应任务通过。它只恢复本地存储，不能撤销服务端提交或云数据库写入。
