# 两种问题修复方式

## 共用：先定义问题

记录每条发现的来源、所属测试项目、证据、触发条件、预期与实际行为，以及是否直接发生或由故障注入得到。检测途径不决定分类：用代码测试流程行为，仍归流程测试。

每条给出是否应修复、优先级、处理对象、理由与重测方式。工具告警、待确认线索和工程缺陷分开；不为消除数字盲改代码。其他测试里发现的额外问题纳入同一清单，标明归属和处理范围。

## 第一套：本身检测项目的修复逻辑

用于用户明确要求修复某检测项，或完整修复中的局部步骤。

1. 从证据确定可重复验证的检测项。例如失败仍提示成功、某字段引用错误、具体元素横向溢出。
2. 备份本次修改文件；定位本项原因，做最小修复。
3. 使用原触发条件重测，检查本项缺陷消失及相关正常行为没有退化。
4. 未通过先区分修复无效、产生退化或测试工具失败；授权范围内继续定位和修正。确认引入退化或用户要求时回滚本次修改；通过则标“检测项已修复”。

必须写清证明范围。“失败提示已修复”不能写成“存储问题已解决”；“编译通过”不能写成“业务功能正确”。

## 第二套：完整修复逻辑

用于用户要求解决问题、恢复正常使用，或要求将应修问题完整修好。

1. **确定用户结果**：把问题转成可观察的最终业务结果，先分清症状与根因。
2. **复现和定位**：获取实际错误及环境证据，追踪相关数据和调用链。注入异常用于验证容错；不能将注入的原因认定为真实根因。
3. **覆盖相关分支**：正常成功、失败反馈、重试/恢复、数据一致性；根据业务选择必要分支，不机械增加测试。
4. **修复并局部重测**：按第一套修复具体检测项，保持最小范围，不用隐藏错误或修改文案代替原因处理。
5. **验证最终结果**：在用户授权的环境里完成相应流程，核对结果是否真实存在、可读及持续有效。需要真实写入、重启或其他副作用时检查授权和数据保护条件；不得擅自清数据。
6. **判断完成**：只有目标结果与相关关键分支均验证后，才标“完整修复已验证”。未拿到真实环境证据时标“检测项已修复，完整验证未完成”，列出具体缺口。

示例：保存问题不能只看 toast。验证合法账目写入、金额/日期/分类正确、读取与统计一致、重新进入或重启后仍存在。真实失败时获取存储异常和状态，解决已证实的原因；存储耗尽等环境条件不一定能靠代码强行消除，应明确条件和可执行恢复办法。不能许诺无条件保存成功。

## 两套如何配合

- 两种方式区别在验证范围，不按测试项目划分；代码、UI、点击、流程都适用。
- 单项修复可作为完整修复的一步，不能自动升级为完整完成。
- 用户明确限定某项时尊重范围；未限定且要求解决问题时，继续验证最终目标。
- 没有真实故障、仅发现容错缺陷时，修容错并明确证据来源；验证正常路径，不虚构真实故障或修复结果。
- 重测失败时保留证据，按实际原因决定继续修正或回滚，不覆盖用户后续修改；扩大副作用或授权范围前明确说明。

## 交付状态

每项至少列出：应否修复、修复方式、已改内容、实际重测、剩余问题/缺口。

问题状态统一按 reporting.md：未修复 / 已改待复测 / 复测通过 / 复测失败 / 待确认。另记修复方式（检测项修复/完整修复）、验证范围和是否已回滚。“检测项已修复”“完整修复已验证”仅说明已验证范围，不另创一套状态。

同时保留正常路径、异常处理、根因解决、最终结果验证各自的事实，不合并成笼统“已修复”。

## 问题分级与自动修复（原 SKILL.md“证据与问题处理”）

判断严重性与是否自动修复是两件事。

- **确定缺陷**：有实际证据及可重复验证的预期。仅当修法明确、范围最小且在用户授权内时修复。
- **待确认**：存在业务前提、设计取舍或启发式误判可能。说明证据和不确定性，交用户定夺。
- **未覆盖 / 无结论**：工具不可用、通道失败、元素不唯一、缺少测试数据或未执行。不能计作通过。

脚本的严重性标记只是线索，不能仅凭级别决定修复。横向溢出可能有多种根因，先定位再选修法，不能用 `overflow: hidden` 掩盖；缺失页面、图片或绑定字段通常也有多种修法。

区分真实发生与故障注入：模拟存储失败可证明异常处理缺陷，不能证明实际环境存在写入故障。
